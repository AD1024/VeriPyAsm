# Prototype implementation plan

Design baseline: 2026-11-04. This document describes the roadmap. The scaffold and
[first bytecode slice](BYTECODE.md) are implemented: a limited decoder, scalar
semantics, certified shallow translation, and checked stack admission. Stack
certificates have semantic preservation, capacity, underflow-exclusion, and return
shape proofs. Fused local instructions and extended operands are supported, and
the imported `triangular` loop is stack-admitted. The [contract interface](CONTRACTS.md)
and universal total-correctness proofs for imported integer `add1` and nonnegative
integer `triangular` are implemented. Sound [instruction, block, and loop rules](RULES.md)
compose these proofs. M1/M2/M3 remain incomplete: broader fragment coverage and
program case studies are pending. M4 now includes hand-extracted closed VCs and
conditional assembly for triangular; automatic generation and the registry remain.

The [verification-flow design](DESIGN.md) defines the current interface decisions:
externally generated bytecode input, shallow semantic elaboration, closed VCs,
manual proof registration, and configurable checked/solver-trusted discharge.

## 1. Objective and proof boundary

Given an externally generated bytecode artifact for a pinned CPython release,
import its code-object data and prove a user-supplied specification in Lean 4.
The first deliverable is a complete proof for an integer loop, including
termination and absence of Python exceptions under its precondition.
This deliverable is now implemented for the imported `triangular` artifact.

The long-term unit of verification is a component with an interface contract:
its results, exceptions, heap effects, and observable interactions. This supports
both terminating functions and services that intentionally run indefinitely.

Distinguish three obligations throughout the project:

1. **Artifact identity:** the code and environment described by the theorem are
   the ones supplied to the runtime.
2. **Program correctness:** executions in the Lean semantics satisfy the contract.
3. **Runtime correspondence:** the selected CPython implementation realizes that
   semantics, under stated runtime and resource assumptions.

The prototype proves (2). It records and checks evidence for (1), initially
trusting extraction and the external comparison with the executed code object.
It investigates (3) through implementation inspection and differential testing;
these are evidence, not a refinement proof. Verifying a concrete compiled artifact
does not require proving the source compiler correct, but it does not establish a
general source-to-bytecode preservation theorem either.

## 2. Initial target and Python fragment

Pin Lean 4.34.0, matching the reviewed Crush toolchain, and CPython 3.14.4.
Begin with baseline bytecode from a conventional,
single-threaded CPython build, `optimize=0`, without tracing, monitoring callbacks,
custom frame evaluators, or external mutation of the running program. Record the
interpreter build identity as well as its release. CPython's bytecode is an
implementation detail with no cross-release compatibility guarantee. [1]

Use mathematical unbounded integers and assume sufficient runtime resources.
The initial theorem excludes allocation failure, asynchronous signals, and
runtime implementation bugs. Specialized execution and JIT execution are outside
the first formal model; claiming the same result for those execution paths needs
an explicit correspondence assumption or a later refinement proof.

### Prototype P0: scalar, sequential functions

| Aspect | Included behavior |
| --- | --- |
| Entry points | Ordinary top-level functions, fixed arity, positional arguments, no decorators, defaults, closures, or global dependencies |
| Values | Exact built-in `int`, `bool`, and `None`; arbitrary-precision integers represented by Lean `Int` |
| Numeric operations | `+`, `-`, `*`, `//`, `%`, unary `+` and `-`; supported in-place forms on these immutable scalar values |
| Boolean behavior | Truthiness, `not`, short-circuit `and` and `or`, including their operand-returning behavior |
| Comparisons | Equality/inequality over supported values and ordered numeric comparisons; correct bool/int interaction |
| State | Local assignment, including reassignment to another supported value type, and explicit uninitialized local slots |
| Control flow | Conditionals, `while`, `break`, `continue`, returns, and their compiled jumps |
| Exceptions | Modeled outcomes for supported failing operations, including division by zero, invalid operand types, and unbound locals |
| Proofs | Functional correctness, absence of unexpected exceptions, invariant preservation, and termination where claimed |

Arithmetic must preserve Python's floor-division and remainder rules for negative
operands. Do not assume that Lean's default division notation has the required
meaning. Boolean numeric coercion must respect `True == 1` and `False == 0`.
An annotation such as `n: int` does not establish an input precondition: the
contract must require an exact built-in type or cover all accepted runtime tags.
User-defined subclasses and overloaded operators are deferred. [2]

Initially exclude floats, strings, containers, indexing, object identity tests,
user function calls, imports, attributes, classes, reflection, generators,
coroutines, exception handlers, and explicit `raise`. Float support must eventually
model binary floating point and exceptional values, rather than replace them with
real numbers. Mutable containers will require a heap and aliasing semantics.

This table describes useful source idioms, not a new Python parser or a promise
that every spelling is accepted. Admission is determined by the compiled code
object, supported opcode/operand combinations, and semantic preconditions.
Reject unsupported code-object features and instructions with an offset and reason.
Never replace an unsupported operation by a no-op, successful return, or invented
Python exception. A reachable operation that leaves the supported value fragment
is a verification gap, not a valid outcome.

### First instruction inventory

Inventory instructions from actual compiled examples before implementing them.
The local CPython 3.14.4 `triangular` example already emits:

```text
RESUME                         LOAD_SMALL_INT
STORE_FAST                     LOAD_FAST_BORROW
COMPARE_OP                     POP_JUMP_IF_FALSE
NOT_TAKEN                      LOAD_FAST_BORROW_LOAD_FAST_BORROW
BINARY_OP                      JUMP_BACKWARD
RETURN_VALUE                   CACHE entries
```

A Euclidean GCD loop also emits `LOAD_FAST_LOAD_FAST` and
`STORE_FAST_STORE_FAST`. Therefore a baseline decoder must handle compiler-emitted
fused instructions, even before runtime specialization. Implement packed operands
and exact load/store ordering from the pinned source. Preserve the complete
`COMPARE_OP` argument, including flags, and distinguish `BINARY_OP` variants. [3]

Extend the inventory for constants, boolean branches, unbound-local checks, stack
operations, and large operands as the corpus grows. `EXTENDED_ARG` and inline cache
layout belong to decoding. Cache words are payload, not ordinary executable NOPs.
Retain byte offsets and version-specific jump origins. Abstracting `RESUME`,
`NOT_TAKEN`, borrowing, and ownership bookkeeping is justified only within the
stated runtime profile and scalar fragment. [1, 3]

## 3. Formal specifications

### P0: relational contracts with two exit cases

Write contracts as Lean propositions over an initial state, a final state, and
the outcome. Keep the specification independent of the bytecode being verified.
The notation below is schematic. The implemented [Lean API](CONTRACTS.md) uses
native predicates with ghost inputs and explicit initial/final frames:

```text
{ P(initial) } code { normal: Q(initial, final, result),
                     raises: E(initial, final, exception) }
```

A partial-correctness contract requires that, for every admitted initial state
satisfying `P`:

- Every reachable state remains well formed and within the supported semantics.
- Every finite terminating execution satisfies `Q` or `E`, as appropriate.
- No execution reaches an internal VM fault or an unsupported semantic case.

This allows divergence but does not allow a stuck state to make a proof vacuous.
The current generic contract rules prove exclusion of explicit VM faults; stack
capacity follows from the separate admission certificate under its entry
assumptions. Additional reachable-state invariants need their own proofs.
Setting `E = False` expresses absence of Python exceptions under the precondition.
Initially, exception observations expose exception kind; message text, traceback
identity, and exception-object inspection are deferred.

Total correctness adds that every maximal execution terminates with an allowed
outcome. For deterministic P0, establish this with a loop ranking function or a
well-founded argument. A successful run for one fuel value on one input is only
an execution fact, not universal correctness or a termination proof.

The fuel-bounded executable evaluator returns an explicit inconclusive result on
fuel exhaustion. That is distinct from a Python exception, a future application
timeout, suspension, and semantic unsupportedness.

### First loop theorem

For `examples/python/triangular.py`, let `N` be the initial mathematical integer:

```text
Pre:     the argument has exact built-in type int and N >= 0
Normal:  the result is an integer r and 2*r = N*(N + 1)
Raises:  False
Total:   execution terminates
```

At the loop header use `n >= 0` and
`2*s + n*(n + 1) = N*(N + 1)`; use `n` as the decreasing natural-number measure.
The implemented proof relates locals, an empty operand stack, and PC 6 to this
mathematical invariant. Its rank is `n.toNat`, compared only on back edges;
nonnegativity and the positive test establish strict decrease. A nonempty
iteration reaches PC 6 again or the exit at PC 58. The entry, iteration, and
return summaries are proved from the actual imported instruction lookups.
`triangular_artifact_total` quantifies over every valid `N` and anchors the
contract to the raw artifact through its translation certificate.

Further case studies will cover branching absolute value, iterative factorial, Euclidean GCD for
nonnegative inputs, and a division function with normal and zero-divisor cases.
These exercise branching, nonlinear specifications, simultaneous assignment,
signed arithmetic semantics, and exceptional outcomes.

### Later specifications: effects, traces, and progress

Extend contracts with heap footprints and frame conditions when mutation arrives:
which locations may change, which remain unchanged, and what aliasing is allowed.
Use separation-style assertions where ownership makes composition simpler;
retain relational heap predicates for intentional sharing. Prove the appropriate
frame rule before using it as automation.

For effectful and asynchronous components, use finite and infinite observable
traces. Safety means every permitted execution obeys a trace/state invariant;
liveness means an eventuality on all executions satisfying explicit scheduler and
environment assumptions. Candidate specifications include:

- A function returns a sorted permutation of its input and preserves other objects.
- A resource is never used after it is closed.
- Cancellation triggers the required cleanup before the task reports completion.
- A request eventually receives a response, assuming the dependency responds and
  the relevant work is scheduled fairly.
- A server maintains its protocol invariant indefinitely, without requiring termination.

Relate observable traces to an abstract reference component by refinement. Keep
return-value contracts as a simple special case. Fair scheduling alone cannot
guarantee network responses or progress by a task that never yields.

## 4. Semantic architecture

Use an executable small-step machine as the basis of a relational execution
semantics. The following are module boundaries to introduce as milestones need
them, not empty modules to generate immediately:

| Planned module | Responsibility |
| --- | --- |
| `CPython/V314/Artifact` | Raw bytes, constants, metadata, source/build provenance |
| `CPython/V314/Decode` | Version-specific opcodes, cache widths, prefixes, packed operands, offsets |
| `Semantics/Value` | Tagged scalar values first; reference-backed objects later |
| `Semantics/Frame` | Code reference, PC, locals with unbound slots, operand stack |
| `Semantics/Step` | Instruction transitions and supported operation semantics |
| `Semantics/Execution` | Multi-step execution, outcomes, traces, and bounded evaluator |
| `Logic/Contract` | Normal/exceptional contracts and termination definitions |
| `Logic/Rules` | Sound instruction, block, branch, loop, and later call rules |
| `Automation/Crush` (later) | Configurable checked/solver-trusted discharge and per-VC provenance |
| `Examples` | Theorems about concrete imported artifacts |
| `Runtime` (later) | Heap, call stack, builtins, external-operation contracts |
| `Async` (later) | Suspended continuations, tasks, futures, scheduler, cancellation |

P0 can use a total `step` function. Define the transition relation from it, or prove
their equivalence if separate definitions are useful. Prove determinism and
state-validity preservation under suitable hypotheses. Keep instruction dispatch
separate from value operations so object semantics can expand without rebuilding
the control-flow logic.

Machine state is explicit data, not a Lean recursive evaluation call that loses
its continuation. P0 uses one frame; calls introduce a stack; suspension later
preserves the relevant continuation. Reserve conceptual boundaries for local VM
steps and external events without implementing a universal scheduler now.

Keep decoded instructions as the artifact's reference representation, then
elaborate proof-facing syntax into shallow Lean semantic combinators for blocks.
Prove correspondence with the original machine, including outcomes, relevant
termination behavior, and traces up to internal steps. Splitting fused instructions
or restructuring control flow must preserve that connection. Scalar-by-value
representation is justified by excluding observable scalar identity; introduce
heap references before supporting mutable containers and demonstrate preservation
of the earlier scalar fragment. See [the flow design](DESIGN.md).

## 5. Artifact import and validation

1. Accept artifacts from external compiler/extractor tools; source generation is
   outside the verifier. Require the exact interpreter/profile and sufficient
   function/environment metadata. Reject context P0 cannot represent. A code
   object's name does not establish identity with a runtime binding.
2. Require baseline `co_code`, tagged constants, argument/local/name metadata,
   flags, stack size, and exception-table bytes, with lossless large integers.
   Record schema version, implementation/release/build, compilation settings,
   function selection, and artifact digest; source provenance is optional.
3. Decode the raw representation in Lean. Check instruction boundaries, cache
   layout, valid operands, indices, target boundaries, stack behavior, and supported
   code-object features. P0 requires empty exception tables and excludes generator
   and coroutine flags. A stack analysis must account for branch-specific effects.
4. Generate literal Lean artifact data plus a kernel-checked fact that decoding
   and validation succeed. The generator proposes data/proofs; Lean checks the
   claim relative to those literal inputs. This does not prove extraction fidelity.
5. Compare imported bytes and metadata with the actual code object used in the
   conformance harness. Document this external identity check as trusted until a
   stronger checked loading path exists. Hashes identify artifacts; they do not
   independently prove their origin or execution.

Use `dis` as a readable oracle during development, not as the only retained
representation. Defer a `.pyc`/marshal loader until the code-object path works.
When calls and globals are added, bind their environment and dependency versions
to the contract as well: a code hash alone does not bind mutable globals or callees.

## 6. Implementation milestones and completion criteria

| Stage | Work | Evidence required to finish |
| --- | --- | --- |
| M0 — scaffold (complete) | Pinned Lake library, target metadata, example, plan, optional Crush experiment target | `lake build` succeeds; `lake build CrushObligations` checks the separate experiment |
| M1 — artifact path (partial) | External artifact schema/loader, exact-version check, decoder, admission checker, opcode inventory | Real `add1`, branch, and loop artifacts decode; malformed offsets, operands, cache layouts, and unsupported features are rejected; artifact round trips are checked |
| M2 — executable semantics (partial) | Scalar operations, frame transitions, exceptions, execution relation, bounded runner | Determinism/preservation lemmas; interpreter/relational agreement; differential results for normal and exceptional cases |
| M3 — first program proofs (partial) | Universal `add1` and total `triangular` proofs implemented using sound instruction/block/loop rules; additional branching and arithmetic case studies remain | Universal, kernel-checked `add1`, branching, and total `triangular` theorems about imported artifacts, with no `sorry` or project-specific axioms |
| M4 — reusable prototype (partial) | Proved loop rules, hand-extracted closed VCs, and conditional assembly implemented; invariant annotations, automatic VC generation, proof registration, and configurable Crush integration remain | Factorial, GCD, and division contracts; changed artifacts invalidate stale cached proofs; assurance and pending obligations are reported |
| M5 — sequential real-world slice | Calls, heap-backed lists/dicts, aliases, selected builtins, exception handlers/finally | A selected real function with verified dependency contracts, mutation/frame properties, and both exit cases |
| M6 — async slice | Resumable coroutines plus a scoped scheduler/future/task model | A small actual asyncio program satisfies a safety property across permitted schedules; a progress property states its fairness and environment assumptions |

The current M1/M2 slice checks stack heights across both normal branch edges and
loops, exact return shape, and `co_stacksize`. A worklist proposes a finite table;
an independent Lean proposition checks it and supports execution proofs. This
does not establish value tags, local initialization, exception freedom, or
termination. Fused local operations now extend the stack soundness proofs;
prefix grouping preserves cache-aware jump origins and rejects interior entry
points. The broader artifact loader remains pending; see the
[implemented interface and proof boundary](BYTECODE.md).

Finite execution and reachability now agree with the bounded runner. Native
normal/exceptional contracts distinguish partial correctness from termination;
the imported `add1` proof covers every integer and excludes exceptions and faults.
Changing its small-integer operand yields a freshly admitted artifact that
provably violates the original contract.

Instruction/block rules distinguish continuation, return, and exception
postconditions, preserve first-exit boundaries, and connect to the original
execution semantics. Loop invariant and well-founded ranking rules now prove
`triangular` totally correct. Its arithmetic obligations use checked Lean tactics
without a new dependency. A freshly admitted addition-to-subtraction mutation
fails the functional contract despite retaining valid stack behavior.

Named, closed VCs and a conditional assembly theorem are now extracted from this
manual proof. The assembly imports no VC proof provider; all four proofs are
explicit premises. Next comes exact-match proof registration for these named
obligations, followed by reporting and configurable Crush discharge. Automatic
generation, additional P0 case studies, and opcode coverage remain part of the
broader prototype roadmap.

M1–M4 constitute the first prototype. Prove one loop before building a general
verification-condition generator. If arithmetic support warrants Mathlib, add a
Lean-compatible pinned dependency then; keep executable semantics independent of
proof-automation dependencies where practical.

Use Crush as the first automation backend to evaluate. Its integration boundary is
the logical obligations produced by proved semantic rules, not an unchecked
translation of a Python function directly to SMT. Default to strict reconstruction;
allow explicitly configured solver trust with distinct reporting and aggregate
assurance. Audit theorem dependencies. Keep the runtime semantics independent of the
solver package. See [the integration assessment](CRUSH.md) and
[`experiments/CrushObligations.lean`](../experiments/CrushObligations.lean) for the
initial experiment. These five obligation proofs are not yet bytecode proofs.

For M1/M2, compile small functions with boundary values and negative arithmetic;
compare results, runtime types, and exception kinds with CPython. Include zero
divisors, unbound locals, bool/int interactions, large constants, large jump
offsets, fused operations, and both branch directions. Use an independent expected
result source where possible, not the decoder's own output as its sole oracle.
Conformance tests support the semantics but do not prove it correct.

For M3/M4, deliberately alter a relevant instruction/constant to ensure an existing
contract fails or needs a new proof. Audit theorem assumptions and axiom use;
avoid `sorry`, unchecked external-solver answers, and `native_decide` in the claimed
kernel-only proof path. Distinguish proof checking from executable evaluation.

## 7. Route to asynchronous Python

Async support requires three distinct models: the Python coroutine protocol,
the selected asynchronous library/runtime, and the external environment. CPython
bytecode semantics alone cannot specify event-loop behavior. The event loop runs
tasks and callbacks and mediates I/O; its contract must be explicit. [4, 5]

### A. Establish sequential foundations first

Add call frames, heap identities, exception propagation, and `try/finally` before
claiming cancellation-safe programs. Support library calls either by verifying
their bytecode transitively or by explicit contracts for primitives and native
extensions. A contract for a socket or database operation is an assumption about
that dependency until separately justified; Python cannot expose its C/OS
implementation merely through bytecode.

### B. Add resumable execution

Represent coroutine lifecycle and saved frame/continuation explicitly. Model
creation, resumption with a value or exception, suspension, completion, and
cleanup. Calling an async function creates a coroutine; it does not by itself
schedule a task. Awaitables include coroutines, tasks, and futures. [4, 6]

Implement the relevant 3.14.4 opcodes from an actual async corpus and the pinned
source, rather than translating `await` into an arbitrary blocking instruction.
Awaiting something already complete need not switch tasks; suspension and task
scheduling must be separate transitions. Eager task construction can also execute
coroutine code synchronously, so the first supported scheduler profile should
explicitly exclude eager execution and reject it until modeled. [4]

### C. Add a scoped asyncio runtime

Start with one event-loop thread, cooperative tasks, futures, and a small identified
set of `asyncio` primitives. Maintain task states, runnable/waiting sets, future
results, and heap ownership/sharing. Model external completions nondeterministically
subject to named environment contracts. Handle timer ordering and logical time
before claiming timeout properties. [4, 5]

Separate a deterministic executable scheduling policy for testing from the
relation of allowed schedules used in proofs. A universal safety proof must
cover every schedule admitted by that relation, including external callbacks.
Document any deliberate over-approximation and show that the target runtime's
behaviors are included, conditionally at first. Avoid claims based on one tested
interleaving. Do not insert task switches after every bytecode: admissible
interleavings must follow the chosen runtime model.

### D. Add cancellation and structured concurrency

Cancellation is a request delivered through exception behavior, not immediate
task deletion. Cleanup and suppression matter. Task groups and timeouts add
further cancellation and exception behavior; they need dedicated contracts. [4]

First support one documented cancellation profile and establish cleanup properties.
Then add repeated cancellation, shielding, task groups/exception groups,
asynchronous context managers, and async iteration as separate extensions.
Identify unsupported primitives/configurations at admission or contract resolution.

The first async case study should use two tasks and a future or queue. Prove a
resource/protocol safety invariant across all admitted schedules. After adding
cancellation, prove cleanup on all allowed exit paths. State progress separately:
for example, completion given dependency responsiveness, sufficient resources,
termination of local computation, and the required scheduling fairness. A blocked
future is neither a semantic failure nor evidence of termination.

Thread pools, multiple event loops, free-threaded Python, and native callbacks
that share mutable memory require a concurrency/memory model beyond this first
async profile. Keep them as an explicit later stage rather than silently treating
all asynchronous programs as single-threaded cooperative tasks.

## 8. Decisions to revisit using evidence

- Select the first real library routine after M4, then prioritize heap/object and
  dependency features based on its actual bytecode and contracts.
- Evaluate PyStar's operational design and inspect LeanPy before claiming novelty
  or choosing to reuse code. No external formalization is currently a dependency.
- Decide when a verified decoding/normalization boundary saves enough repeated
  proof work to justify another semantics layer.
- Choose a concrete asyncio version/profile and case study before implementing
  the scheduler. The first async claim should identify supported primitives and
  environmental assumptions as precisely as the initial integer fragment.
- Runtime refinement remains a separate research track. A tested executable model
  is useful without claiming that the CPython binary has been verified.
